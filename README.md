# Riburaju Family Budget

A private, secure family finance dashboard for **riburaju.com** — income, expenses,
accounts, budgets, savings goals, planned expenses, analytics, and reports, built
so a real family can use it every day on a phone or a laptop.

This is a real, working application, not a mockup: every page reads and writes
real data through Supabase (PostgreSQL) with Row Level Security, every button
does what it says, and the numbers on the dashboard are calculated live from
your transactions — nothing is hardcoded.

## What's included

- **Authentication**: email + password via Supabase Auth, brute-force login
  throttling, password reset, invite-only registration (no public sign-up
  form anywhere), full session protection on every private route.
- **Dashboard**: live income/spending/savings/remaining-budget cards, cash vs.
  bank balances, total available money, planned-expense impact, recent
  transactions, mini budget and account widgets.
- **Income & Expenses**: fast add/edit/delete, categories & subcategories,
  payment methods, income sources, receipt uploads, search/filter/pagination,
  period totals (this month / last month / this year).
- **Transfers**: move money between accounts without ever touching your
  income/expense totals.
- **Accounts**: cash, bank, savings, credit card — balances computed
  automatically from opening balance + transactions + transfers.
- **Monthly Budget**: per-category limits with 🟢🟡🟠🔴 status, remaining
  amount, over-budget warnings.
- **Budget Planner**: a 6-step wizard (income → essentials → flexible spending
  → savings goals → planned expenses → review) that warns you if your plan is
  in deficit and suggests where to cut back.
- **Savings Goals**: multiple goals, deposits/withdrawals, progress bars.
- **Planned Expenses**: track future spending and convert a plan into a real
  expense with one click.
- **Recurring Transactions**: salary, rent, subscriptions, etc. — posted
  automatically by a daily job, never duplicated.
- **Analytics**: category donut, monthly bar chart, income vs. expense line,
  budget vs. actual, savings trend, spending-by-account/payment-method, and
  auto-generated plain-language insights.
- **Reports**: monthly, annual, income, expense, category, budget, savings,
  and account-balance reports, plus a full filterable transaction history —
  all exportable to CSV, all printable to PDF via the browser.
- **Financial Calendar**: every income/expense/transfer/planned/recurring
  item plotted on a month grid.
- **Notifications**: budget exceeded/near-limit, low balance, upcoming
  planned expenses, savings goals reached, recurring payments due soon —
  generated by a dedup'd daily job so you're never spammed.
- **Settings**: profile & password, family member invites & roles,
  category management, application (currency/name) settings.
- **Responsive, mobile-first UI** with a bottom nav + one-tap "Add Expense"
  on phones, a sidebar on desktop, and light/dark mode.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 16 (App Router) + TypeScript | One deploy target for frontend + API routes, great Vercel/GitHub integration |
| Styling | Tailwind CSS | Fast, consistent, small bundle |
| Database + Auth | Supabase (PostgreSQL + Auth + Storage) | Generous free tier, real Postgres with Row Level Security, easy to self-host later if ever needed |
| Charts | Recharts | Solid, well-documented, accessible defaults |
| Forms/validation | react-hook-form + Zod | Same validation schemas run in the browser *and* on the server |
| Hosting | Vercel | Native Next.js support, free tier is plenty for a family app, trivial GitHub → deploy pipeline |

## 1. Create your Supabase project

1. Go to [supabase.com](https://supabase.com) → **New project**. The free tier
   is enough for a family (500MB database, 1GB file storage, 50k monthly
   active users).
2. Note your **Project URL** and **anon public key** (Project Settings → API)
   — you'll need these for `.env.local`.
3. Also note the **service_role key** on that same page. This key bypasses
   every security rule — never put it in `NEXT_PUBLIC_*`, never commit it,
   never send it to the browser. It's used only inside a handful of server
   routes (see [Security](#security)).

## 2. Run the database migrations

In the Supabase dashboard, open **SQL Editor** and run each file in
`supabase/migrations/` **in numeric order** (0001, 0002, 0003, ...) — each one
builds on the last. Alternatively, if you have the
[Supabase CLI](https://supabase.com/docs/guides/cli) installed:

```bash
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

This creates every table, the account-balance view, helper functions
(`current_family_id`, `is_admin`, recurring-transaction generation,
notification generation), and — critically — the Row Level Security
policies that keep one family's data invisible to everyone else.

Optional: after you've created your real admin account (step 5), you can run
`supabase/seed-demo-data.sql` by hand (edit the `admin_email` variable at the
top first) to explore the app with realistic sample income, expenses,
budgets, and goals. It's clearly marked and easy to remove — see the comment
block at the top of that file.

## 3. Configure Supabase Auth

In **Authentication → Providers → Email**:

- Leave **Email provider** enabled (that's how login works).
- **Turn "Allow new users to sign up" OFF.** This app never exposes a public
  registration form anyway (see [Security](#security)), but disabling it at
  the Supabase level too is a second layer of protection — the only ways to
  create an account are the one-time admin bootstrap and admin-issued
  invites, both of which use the service-role key server-side and bypass
  this setting intentionally.
- Under **Authentication → Email Templates**, you can customize the password
  reset email if you like (optional).
- Under **Authentication → URL Configuration**, set:
  - **Site URL**: `https://riburaju.com`
  - **Redirect URLs**: add `https://riburaju.com/auth/callback` (and
    `http://localhost:3000/auth/callback` while developing).

In **Storage**, migration `0005_storage_receipts.sql` already created a
private `receipts` bucket with per-family access policies — no manual step
needed.

```bash
# SUPABASE_SERVICE_ROLE_KEY, ADMIN_BOOTSTRAP_SECRET (generate one: openssl rand -hex 32)

```

Open [http://localhost:3000](http://localhost:3000) — you'll land on the
login page (there's nothing to see without an account yet — see step 5).

Useful scripts:

```bash
npm run dev         # local dev server
npm run build        # production build (also type-checks)
npm run typecheck     # TypeScript only, no build
npm run lint          # ESLint
```

## 5. Create the first admin account

There is deliberately no "sign up" page. The very first account is created
once, through a secret-gated setup route that also creates the family and
seeds the default categories:

```bash
APP_URL="http://localhost:3000" \
ADMIN_BOOTSTRAP_SECRET="the-same-value-as-in-.env.local" \
./scripts/create-first-admin.sh
```

(or call `POST /api/setup/bootstrap-admin` directly with
`{ secret, familyName, currency, adminEmail, adminPassword, adminName }`).

This route refuses to run a second time — once any family exists in the
database, it always returns 403, regardless of the secret. **After you've
created your admin account, remove or rotate `ADMIN_BOOTSTRAP_SECRET`** in
your deployment's environment variables so the route can never be called
again (it's already structurally blocked, but there's no reason to leave the
door even latched).

From there, log in and invite the rest of the family from **Settings → Family
Members** — an admin creates an invite (email + role), copies the generated
link, and shares it directly (WhatsApp, SMS, etc.). The app doesn't send
email itself for invites; it hands you a link to send however you'd like.
Password-reset emails, on the other hand, **are** sent automatically by
Supabase Auth's built-in email sending.

## 6. Deploy to Vercel

1. Push this repository to GitHub (see below if you haven't already):
   ```bash
   git init
   git add -A
   git commit -m "Initial commit: Riburaju Family Budget"
   git branch -M main
   git remote add origin https://github.com/YOUR_USERNAME/riburaju-budget.git
   git push -u origin main
   ```
2. Go to [vercel.com](https://vercel.com) → **Add New Project** → import that
   GitHub repository. Vercel auto-detects Next.js — no build settings to
   change.
3. Under **Environment Variables**, add everything from `.env.example` with
   your real values (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_APP_URL` = `https://riburaju.com`,
   `NEXT_PUBLIC_APP_NAME`, `NEXT_PUBLIC_DEFAULT_CURRENCY`,
   `ADMIN_BOOTSTRAP_SECRET`, and `CRON_SECRET` — generate both secrets with
   `openssl rand -hex 32`).
4. Click **Deploy**. Every future push to `main` redeploys automatically.

## 7. Connect riburaju.com

DNS is not configured by default — you do this once, after the first deploy:

1. In Vercel: **Project → Settings → Domains → Add** → enter `riburaju.com`
   (and `www.riburaju.com` if you want the `www` version too, with a
   redirect to the bare domain).
2. Vercel shows you the exact DNS records to add. Typically:
   - If riburaju.com is your **apex/root domain**, add an **A record**
     pointing `@` to Vercel's IP (Vercel shows the current value — it's
     `76.76.21.21` at the time of writing, but always use what Vercel
     displays for your project).
   - Add a **CNAME record** for `www` pointing to `cname.vercel-dns.com`.
   - If you'd rather point the whole domain at Vercel with one record, use
     Vercel's nameservers instead (shown as an alternative option) — simplest
     if riburaju.com isn't hosting anything else.
3. Go to wherever riburaju.com is registered (your domain registrar) and add
   those exact records in its DNS management panel.
4. DNS propagation usually takes a few minutes, sometimes up to 24-48 hours.
   Vercel's Domains page shows a green check once it verifies.
5. **HTTPS is automatic** — Vercel provisions and renews a TLS certificate
   for riburaju.com the moment DNS verifies. There's nothing else to
   configure; the app is unreachable over plain HTTP once this completes
   (Vercel redirects http → https automatically).
6. Update `NEXT_PUBLIC_APP_URL` in Vercel's environment variables to
   `https://riburaju.com` if you hadn't already, and update Supabase's
   **Authentication → URL Configuration → Site URL / Redirect URLs** to match
   (`https://riburaju.com` and `https://riburaju.com/auth/callback`) —
   password-reset links are built from this and will send people to the
   wrong place otherwise.

## 8. Enable the daily background job

`vercel.json` schedules `GET /api/cron/recurring` once a day (02:00 UTC).
This single job does two things, both idempotent and safe to re-run:

- Posts any recurring income/expense whose due date has arrived, and
  advances that rule's next date.
- Generates the notification alerts described above (budget exceeded/near
  limit, low balance, upcoming planned expenses, savings goals reached,
  recurring payments coming soon), each deduplicated so a family member is
  never notified twice for the same thing.

Vercel Cron calls this route automatically once you have a `CRON_SECRET`
environment variable set — it sends `Authorization: Bearer $CRON_SECRET`,
which the route checks before doing anything. No further setup needed on
Vercel's Hobby or Pro plans. If you deploy somewhere without a built-in
scheduler, call `GET https://riburaju.com/api/cron/recurring` with that same
header from any external scheduler (e.g. GitHub Actions, cron-job.org) once a
day instead.

## 9. Testing authentication

A quick checklist once deployed:

1. Visit `https://riburaju.com` while logged out → you should land on
   `/login`, and every other URL (try `/dashboard` directly) should also
   redirect you there.
2. Log in with the admin account you created in step 5 → you should reach
   the dashboard.
3. Try 5+ wrong passwords in a row → you should get a "too many attempts"
   message (this is the brute-force guard; it resets after 15 minutes).
4. From **Settings → Family Members**, invite a second account, open the
   copied link in a private/incognito window, and complete registration —
   confirm the new member can log in and only sees this family's data.
5. Click "Forgot password?", check that a reset email arrives, and that the
   link logs you into `/reset-password` rather than straight into the app.
6. Log out from the user menu → confirm you're returned to `/login` and
   `/dashboard` is inaccessible again.

## Roles & permissions

Two roles today, designed to extend later (see `family_members.role` and the
RLS policies in `0003_rls_policies.sql`):

- **Admin** — everything a member can do, plus: manage family members and
  invites, manage categories, manage accounts, set budgets, edit or delete
  *anyone's* transactions, change application settings.
- **Member** — view all family financial data, add income/expenses/transfers,
  create savings goals and planned expenses, edit or delete only the records
  *they* created.

Every table is scoped by `family_id`, and every policy checks
`family_id = current_family_id()` — a member of one family can never read or
write another family's rows, even if they somehow guessed an ID.

## Database schema

`families → family_members → {accounts, categories, subcategories,
transactions, transfers, budgets, budget_plans, savings_goals,
savings_contributions, planned_expenses, recurring_transactions,
notifications, audit_logs, invites, login_attempts}` — see
`supabase/migrations/0001_init_schema.sql` for full column definitions and
`0002_functions_triggers.sql` for the computed `account_balances` view and
audit-log triggers. Balances are **never** stored/typed in directly — they're
always `opening_balance + income − expenses + transfers_in − transfers_out`,
computed by that view on every read.

## Security

What's implemented, mapped to the request:

- **Passwords** are hashed by Supabase Auth (bcrypt); this app never sees or
  stores them in plain text.
- **Every private page** is gated twice: `middleware.ts` redirects
  unauthenticated requests before they render, and every Server Component
  also calls `requireFamilyContext()` itself (defense in depth — a page
  never trusts the middleware alone).
- **Family isolation** is enforced at the database level (Postgres Row Level
  Security), not just in application code — even a bug in a page's query
  couldn't leak another family's rows.
- **Brute-force protection**: failed logins are throttled per email
  (5 attempts / 15 minutes) via the `login_attempts` table, checked with the
  service-role key so the throttle itself can't be bypassed from the client.
- **Registration is fully closed**: there is no sign-up form. Accounts are
  created only by the one-time, secret-gated bootstrap route or by an
  admin-issued invite token, both server-side, both using the service-role
  key which never reaches the browser.
- **Secrets**: `SUPABASE_SERVICE_ROLE_KEY` is imported behind
  `import "server-only"` (`src/lib/supabase/admin.ts`) — the build fails if
  it's ever pulled into client code. All secrets are environment variables;
  none are committed (`.gitignore` excludes every `.env*` except
  `.env.example`).
- **Input validation** runs through the same Zod schemas
  (`src/lib/validations.ts`) on both the client (instant feedback) and every
  mutation (Postgres constraints — `amount > 0`, distinct transfer accounts,
  required categories on expenses — as the final backstop).
- **XSS**: React escapes all rendered output by default; the only
  `dangerouslySetInnerHTML` in the app is a static, hardcoded theme-init
  script with no user input anywhere near it.
- **CSRF**: every mutating API route requires a JSON body and reads it with
  `request.json()`, so a classic HTML `<form>` CSRF post (which can't set
  `Content-Type: application/json`) fails outright; a cross-origin `fetch`
  CSRF attempt is blocked by the browser's CORS preflight, since this app
  never sends `Access-Control-Allow-Origin` headers. The two Supabase
  mutation paths (direct client calls) are protected by RLS regardless of
  what triggered the request.
- **File uploads**: receipts go to a private Storage bucket, size-capped
  (5MB) and MIME-type-restricted (`jpeg/png/webp/pdf` only) at the bucket
  level, with per-family Storage RLS policies mirroring the database ones.
- **Security headers**: HSTS, `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, a restrictive `Permissions-Policy`, and
  a conservative `Referrer-Policy` are set on every response
  (`next.config.js`).
- **No client-side leakage**: every Supabase query the browser makes goes
  through the anon key + RLS; nothing sensitive is exposed via a public API
  route (`/api/health` returns a static `{status:"ok"}` and nothing else).

## Known limitations

Being upfront about what's simplified rather than pretending it's finished:

- **Invite emails aren't auto-sent.** An admin creates an invite and shares
  the link manually. Wiring up an email provider (Resend, Postmark, or
  Supabase's own SMTP relay) to send it automatically is a small, isolated
  addition — the invite/token model is already there, it would just also
  send an email from `/api/invites/accept`'s sibling creation path.
- **PDF export is browser print, not a generated file.** "Export CSV" on the
  Reports page produces a real file; "Print / PDF" opens the browser's print
  dialog against a print-friendly layout, which any browser can save as a
  PDF. A dedicated PDF-generation library could replace this later if a
  literal downloadable `.pdf` matters more than the CSV + print combo.
- **`fiscal_month_start_day`** (Settings → Application) is stored but not
  yet threaded through the month-boundary calculations on the dashboard,
  budgets, and analytics pages — those currently always use calendar-month
  boundaries (1st to end of month). Wiring it through is mechanical (swap
  `monthRangeISO()` for a fiscal-day-aware version) but not done yet.
  self-review found this exact gap.
- **Deleting a transaction doesn't delete its uploaded receipt file** from
  Storage — the file becomes orphaned rather than actively harmful (it's
  still private, still inside that family's RLS-protected folder), but a
  cleanup job could remove it.
- **One family per login**, by design — this is a single-family app, not a
  multi-tenant platform where one person manages several households. The
  schema (`family_id` on every table) would support it with a UI to switch
  active family, but that's out of scope here.

## Maintenance

- **Keeping types in sync**: `src/types/database.ts` is hand-written to match
  the migrations. After changing the schema, regenerate it for full accuracy:
  ```bash
  npx supabase gen types typescript --project-id YOUR_PROJECT_REF > src/types/database.ts
  ```
- **Adding a migration**: create `supabase/migrations/000N_description.sql`,
  run it via the SQL Editor or `supabase db push`. Never edit an already-run
  migration file — add a new one.
- **Rotating secrets**: `SUPABASE_SERVICE_ROLE_KEY` can be rotated from the
  Supabase dashboard (Project Settings → API) at any time; update it in
  Vercel's environment variables and redeploy.
